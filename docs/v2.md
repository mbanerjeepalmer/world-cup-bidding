User experience:
- We need a dead simple homepage.
- It should explain:
  - what the user's next steps are (i.e. sign in and bid),
  - what the constraints are (i.e. only one team per person, countdown to first/last lot closing), and
  - how scoring works (i.e. ratio between price paid and points achieved),


Decisions:
- Work out deployment platform and persistent storage. Optimise for simplicity. Options:
  - I have a Coolify box, so SQLite and Dockerfile.
  - Cloudflare all the way (my preference, just check it's smooth locally).
  - Vercel + Turso.
- Auth:
  - Either use Resend and roll our own with magic links.
  - Or use Clerk.


## Findings

### Deployment: Coolify + SQLite + Dockerfile

Chosen despite the Cloudflare preference, because for this codebase Cloudflare
is a rewrite, not a deploy target:

- The whole server layer is **synchronous `better-sqlite3`** (`db.prepare(...)`
  in `db.ts`, `auth.ts`, `auction.ts`, `scoring.ts`, `sync.ts`, plus a sync
  `db.transaction` around `placeBid`). D1 is async-only, so every query and
  every `load`/action up the call chain would need rewriting.
- `db.ts` creates and seeds the database from the filesystem at import time;
  Workers have no filesystem — that becomes D1 migrations.
- The hourly feed sync runs in-process via `setInterval` in `hooks.server.ts`;
  Workers have no long-lived process — that becomes a Cron Trigger.
- To be fair to the option: Cloudflare's *local* story itself is now smooth
  (`@cloudflare/vite-plugin` runs dev in workerd with local D1). The cost is
  the migration, not the tooling. Vercel + Turso has the same async-rewrite
  problem (libsql client), and serverless kills the in-process sync too.

Coolify cost: a ~20-line `Dockerfile`, nothing else. Verified locally:
`docker build` succeeds (better-sqlite3 prebuilds work on `node:22-slim`),
the container boots, seeds SQLite on a volume, serves pages, and logs
magic links. Configuration: volume at `/app/data`, `ORIGIN` set to the
public URL, port 3000. See README → Deploying to Coolify.

### Auth: Resend magic links (rolled our own)

- Clerk would externalise the user store, but bids/sessions foreign-key into
  the local `users` table and the first-registrant-becomes-admin plus
  domain-tenancy logic live there — we'd have to mirror Clerk users back into
  SQLite (webhooks or upsert-on-request) and maintain both systems.
- Magic links replaced passwords outright: one `login_tokens` table (SHA-256
  hash only, 20-minute expiry, single use), one `fetch` to Resend's API (no
  SDK), and slimmer login/register routes. All password code deleted, with a
  startup migration dropping `password_hash` from v1 databases.
- The emailed link lands on a confirm page with a POST button rather than
  signing in on GET — corporate mail scanners prefetch URLs and would burn a
  single-use token.
- No `RESEND_API_KEY` → links go to the server log (keyless local play);
  `MAGIC_LINK_ECHO=1` → links shown in the UI (dev/e2e only).

### Homepage

Logged-out homepage now leads with live countdowns to the next and final
hammer, then three steps: sign in and bid (email link, no password), one team
per bidder, points ÷ price. Logged-in view unchanged.
